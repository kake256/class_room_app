# 採点運用ルール(2026-07-20制定)

実運用フィードバック(「好きな機械学習」採点、2026-07-20)に基づく標準運用。

## 課題タイプ別の運用

| | 感想文系(KANSOU) | 演習系(EXPERIMENT/DISTANCE/KNN) |
|---|---|---|
| 採点スタンス | **lenient(既定・自動適用)** | strict(既定) |
| 成績簿への入力 | **「全て下書き」のみ** | 「確定のみ入力」でよい |
| 返却 | **TAが満点を含め目視確認してから手動返却** | 自動返却(満点はcandidate_3で人間承認済み) |

### 感想文系を「全て下書き」運用にする理由

- 満点(auto_3)はjudge満点一致で自動確定されるが、実運用でTAの満点基準との
  不一致が約14%(28人中4人)確認された。感想文は満点が学級の大半を占めるため、
  quota等の機械的な絞り込みは機能しない(不一致はシステムの最高確信層で起きる)
- 「全て下書き→目視→手動返却」なら、この不一致をTAが返却前に修正できる。
  2026-07-20の実運用でこの方法により4件すべて捕捉できた実績がある

### 採点スタンスの既定(コードに内蔵)

- KANSOU系ルーブリックは `--lenient` を指定しなくても甘め採点になる
  (rubric.py の DEFAULT_LENIENT_RUBRICS)。`--strict` 指定で上書き可能
- 根拠: 感想文の人間採点は取り組み重視の甘め方針。strict採点は下位帯
  (0〜1点)を沈めすぎる(検証: kansou1/ai_kansou で bias -0.43→-0.25 改善)

## その他の運用メモ

- demoted_from_3フラグ(3点評価からの降格答案)は下書きのみ入力・返却保留になる。
  TAは時間のあるときに「2→3に上げるべきか」だけ抜き取り確認する。
  実運用でTAが「迷った」と感じた答案とこのフラグは高精度で一致した
- 100点/5点満点の課題は、ユーザースクリプトv4.2以降が自動でスケール換算して
  入力する(APIのmax_points)。verifyも自動換算する
- vLLMの長時間運用では必ず `scripts/vllm-server.sh health` で疎通確認してから
  ジョブを投入する(エンジンだけ死ぬクラッシュがあるため)
- refineの審判スタンスは一次採点と揃える(`refine --lenient`)。
  KANSOU系は既定で揃う
