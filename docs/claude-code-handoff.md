# Claude Code 引き継ぎ資料

## 1. このシステムの目的

このリポジトリは、Google Classroom の提出物（PDF、Googleドキュメント、Word等）を取得し、
ローカルGPU上の VLM（vLLM + Qwen-VL）で半自動採点するシステムである。一次採点を複数回行い、
必要に応じて審判モデルによる再採点とペアワイズ比較を行う。最終的には、採点根拠と要確認答案を
人間が確認できる形で集計し、Classroom成績簿へ下書き点を入力する。

主な構成は次のとおり。

- `grader/`: 取得、変換、採点、審判、集計、API、ジョブ管理
- `grader/web/`: 採点・監視用Web UI
- `browser/classroom-grader.user.js`: Classroom成績簿上で動くユーザースクリプト
- `tests/`: 自動テスト
- `run.sh`: Docker経由のCLI入口
- `data/`: 提出物、採点結果、ジョブ状態、ログ（251にのみ置く）
- `config.yaml`: 実行環境固有の設定・認証情報を含み得るため、内容を表示しない

運用・実装の正本は `README.md` と `AGENTS.md` である。この文書と矛盾する場合は、勝手に解釈して
変更せず、ユーザーに確認すること。

## 2. 現在実装されている機能

### CLIと採点フロー

- `list`: Classroom課題一覧の確認
- `run`: 提出物取得、レンダリング、一次採点
- `refine`: judge再採点とペアワイズ比較
- `report`: 集計表示とCSV生成
- `verify`: 人間の確定点との比較
- `watch`: 提出期間中の定期採点
- `push-grades`: APIから直接書ける課題に限った成績書き込み
- `serve` / `api-up`: モデルサーバーまたは採点APIの起動

採点姿勢は `strict`（通常課題向けの厳密採点）と `lenient`（感想文向けの甘め採点）を切り替えられる。
これは `EXPERIMENT`、`KANSOU`、`EFFORT` 等のルーブリック種別とは別の概念であり、ルーブリックは
課題設定から選択される。

### Web UIと永続ジョブ

FastAPIが `/ui/` でWeb UIを配信する。現在、次の操作が可能である。

- Classroom課題一覧とルーブリック登録状態の確認
- `run`、`refine`、`report` の起動
- `run`時の strict / lenient 切り替え
- ジョブ状態とログの確認
- category別集計、要確認答案、根拠、flagsの確認、CSV取得

ジョブ状態は251上の `data/jobs/` に永続化される。API再起動時に実行中だったジョブは
`interrupted` となり、単一vLLMを守るため同時実行は1件に制限される。一次採点モデルと審判モデルの
起動・切り替えは現状手動であり、Web UIは自動切り替えしない。

### `auto_3` と成績書き戻し

`auto_0`〜`auto_2`に加え、judge満点確定、文章量、またはキーワード具体性の条件を満たした
3点答案を `auto_3` としてシステム確認済みにできる。確定理由はflagsで区別される。
`auto_3` は確定組であり、自動入力・自動返却の対象に含める。

重要: **採点Web UI自身はClassroomへの入力・返却を行わない。** UI作成課題にはClassroom APIの
プロジェクト制約があるため、通常の書き戻しは採点APIから結果を読み、ログイン済みClassroom
成績簿上のユーザースクリプトが担当する。

- 「確定のみ入力」: `auto_0`〜`auto_3`を入力し、対象を返却
- 「全て下書き」: 要確認を含めて下書き入力するが返却しない
- 「下書き全削除」: 再採点後の入れ直し用

返却済み答案には触れない設計である。Web UIからユーザースクリプトへの導線は、今後整理すべき
課題として残っている。

## 3. 250 / 251境界とClaude Codeの編集ルール

251 (`/home/kake/classroom-grading-automation`) が主開発・実行作業ツリーである。Claude Codeはここで
コード・文書の編集、git操作、Docker、テスト、サーバー、モデル推論を実施できる。250
(`/home/qwen/classroom-grading-automation`) はCodex Solの対話、設計、レビュー、必要時の小規模変更と
ローカル差分確認に限定し、250でPython実行、Docker、テスト、サーバー、依存関係導入を行わない。

受け渡しはGit中心で行う。旧来の250→251 rsync同期は廃止済みであり、rsyncで251のツリーを上書きしては
ならない。250側の変更はパッチまたはGitブランチとして、251へ明示的に統合する。

1. 作業前後に251で`git status`と対象ファイルの`git diff`を確認する。
2. Claude Codeは作業単位ごとに新規作業ブランチを作成・更新し、自分が新たに作った変更だけをローカルcommitできる。
3. 同一ファイルを250と251で同時編集しない。変更所有者と対象範囲を依頼ごとに明確にする。
4. ブランチ統合、外部への`git push`、`git reset`・`git checkout`などの破壊的操作は、ユーザーの明示承認を得る。
5. `data/`は251だけに保存し、250へコピーしない。結果は251上で匿名集計し、標準出力の要約だけを扱う。

## 4. 現在の作業ツリー

現在、Web UI等にまたがる未コミット・未統合の変更と未追跡ファイルがある。これらは「実装途中」とは
断定せず、所有者不明の既存差分として保護する。

- 既存差分を破棄、巻き戻し、整形による大量変更、上書きしない。
- 明示されていないファイルを変更しない。
- `git reset --hard`、`git checkout --` 等の破壊的操作をしない。
- 既存差分をClaude Codeの判断でcommit、git push、ブランチ統合しない。Claude Codeは自分の新規変更を
  明確に分離できる場合だけローカルcommitできる。
- 作業開始前後に対象限定のdiffを確認し、自分の変更だけを報告する。

既知の **57 passed** は過去の実績であり、現在のツリーに対する保証ではない。必要な確認は251で行う。
通常の全テストは次で実行する。

```bash
cd /home/kake/classroom-grading-automation && \
  docker compose build test && docker compose run --rm test
```

長時間ジョブのログは`data/logs/`へ置く。Claude Codeが本番データを読む検証またはモデル推論を行うのは、
Solまたはユーザーから対象・目的・実行範囲を明示された場合に限る。

## 5. 過去課題の匿名精度評価

感想文3課題の有効答案をまとめた結果は次のとおり。

| 件数 | 完全一致 | ±1点以内 | MAE | bias（システム−人間） |
|---:|---:|---:|---:|---:|
| 206 | 28.6% | 95.1% | 0.777 | +0.641 |

感想文は意図的に甘めに採点しているため、この正のbiasは直ちに欠陥ではない。完全一致率より、
過小評価率と、人間が3点にした答案の見逃し率を主要指標にするべきである。

通常課題では、既知の課題別biasは次の傾向を示した。

| 課題 | bias | 解釈 |
|---|---:|---|
| distance | -0.844 | 明確に厳しすぎる |
| k-NN | -0.412 | やや厳しい |
| application research | +0.600 | 甘めに寄る |
| SVM | +0.121 | 比較的小さい |
| AdaBoost | +0.382 | 甘めに寄る |
| Random Forest | +0.333 | 甘めに寄る |

顔検出は画像中心の超特殊課題であり、通常課題の精度評価や優先改善対象から除外する。上記の
値から通常課題全体の指標を算術で推定せず、必要なら251上の匿名集計処理で再計算すること。

## 6. 優先改善案

1. **distance / k-NN専用基準**: 汎用EXPERIMENT基準の流用を減らし、課題要求と配点に合わせる。
2. **application research調整**: +0.600の甘さを抑えつつ、妥当な高得点答案を落とさない。
3. **再現可能な匿名評価**: 個人情報を含まないfixtureと評価スクリプトをリポジトリ管理し、
   完全一致、±1、MAE、bias、過小評価、3点見逃しを継続計測する。
4. **回帰テスト**: `auto_3`、`apply_length_bonus`、judge満点、文章量・キーワードbonus、
   未確認・人間採点済み答案を下書き対象から除外する境界を専用テストで固定する。
5. **依存関係固定**: `>=`のみの依存指定から、再現可能なlockまたはconstraints運用へ移行する。
6. **Web UIと書き戻し導線**: Web UIとClassroomユーザースクリプトの責務を明確に保ちつつ、
   誤操作を防ぐ状態表示と安全な引き渡しを設計する。
7. **ジョブ運用・モデル切り替え**: モデル状態の可視化、run/refine前提チェック、失敗時の再開、
   排他と監視を改善する。自動切り替えはGPU資源と中断リスクを考慮して設計する。

機能追加より、まず評価データ、回帰テスト、状態定義を固めることを優先する。

## 7. Claude Codeの最初の安全な作業候補

最初の候補は、**新規ブランチと新規ファイルで、採点ロジックを変更しない匿名評価fixture/scriptと
そのテストを設計・実装すること**である。もう一つの安全な候補は、既存の未コミット差分を一切触らずに
レビューと251上のテストを行うことである。

受入条件:

- [ ] 学生名、ID、メール、答案本文、Classroomの実データをfixtureへ含めない
- [ ] 既存の `data/` や検証ログを250へコピーしない
- [ ] 3点満点以外の課題について、正規化規則を明示する
- [ ] 完全一致、±1、MAE、bias、過小評価率、3点見逃し率を定義する
- [ ] 感想文と通常課題を分離し、顔検出を通常集計から除外できる
- [ ] 同一入力から同一集計を再現できる
- [ ] 既存テストを壊さず、251で全テストが通る
- [ ] 変更範囲、実行コマンド、結果、未検証事項を報告する

次点として、distance / k-NNの専用基準案を既存答案を転載せず設計し、小さな匿名ケースで
期待点を先に固定してから実装する。ただし採点方針の変更はユーザー承認を得ること。Claude Codeは
採点方針を独断で変更しない。

## 8. セキュリティと承認が必要な操作

- API token、`.env`、`config.yaml`、`credentials.json`、`token.json` の内容を表示・記録しない。
- 学生名、学生ID、メール、答案本文をログ、diff、報告へ出さない。
- `data/`は251にのみ置き、250へ一括または個別に持ち帰らない（明示指示がある場合を除く）。
- 長時間ジョブのログ全文を転載せず、匿名の件数とエラー種別だけを報告する。
- Classroomへの返却、データ削除、git push、認証・課金設定の変更は、ユーザーの明示承認なしに行わない。
- 成績の下書き入力も実データへの変更である。依頼範囲と対象を確認し、返却と混同しない。
